## The finding that redirected the programme

Raised by the jvector side on 2026-08-25: **is `setSimilarityOrdinals(true)` enabled?**

It is not, and never has been on any cycle:

| check | result |
|---|---|
| `jvector.compaction.similarityOrdinals` default | **`"false"`** (`OnDiskGraphIndexCompactor:375`) |
| Cassandra calling `setSimilarityOrdinals` | **no occurrence in `src/java/`** |
| set on any live JVM | **never** |

This is not a missed knob; it selects a different code path. With similarity ordinals
active the compactor assigns merged ordinals in similarity order — the comment at
`:1580` says this gives *"similarity locality AND sequential record writes at once."*
Without them it falls back to `orderingCache`, which similarity-sorts only **within
coarse ordinal chunks**, because a global sort would *"scatter the single-threaded
writer's pwrites across the whole L0 region."*

And `orderingCache != null` is exactly the condition that enables `clusterMode`:

```java
clusterMode = !seedingActive && orderingCache != null && clusterSearchUsable() && params.fusedPQEnabled;
```

**So the 239 M rescores per merge are not an independent defect — they are the cost of
the fallback we were unknowingly running.** Every result in this campaign, including
all 7 collapses and all four prefetch arms, was measured on that fallback.

## RUN B — `similarityOrdinals=true`. Started 2026-08-25 18:__.

Single variable vs Run A. Zero code: the field initialises from the system property.

**Activation is conditional and can decline silently** — it requires
`fusedPQEnabled && pq != null && pq.getSubspaceCount() >= 4`, and otherwise logs one
INFO line and carries on with the caller's remappers. Two checks, both required
before any Run B number is trusted:

- **absent**: `similarityOrdinals requested but unavailable (requires fused PQ codes)`
- **present**: `L0 source {}: {} nodes in similarity-ordinal order`

### Why: Cassandra never reads back the effective ordinal mapping

The jvector contract has four steps. Cassandra implements three:

| step | `CompactionGraphMerger` | present? |
|---|---|---|
| construct with sources, liveness, caller remappers | :245–248 | yes |
| `setSimilarityOrdinals(true)` | — | **no** |
| `compact(destination)` | :343 | yes |
| **`effectiveRemappers()` read-back** | — | **no** |

It *does* read the retrained PQ codebook back after `compact()` (`:355`), so the
read-back pattern is understood there — just not applied to the ordinal mapping.

The corruption surface is `:432–440`:

```java
var ordinalMapper = new OrdinalMapper.IdentityMapper(totalGlobalOrdinals - 1);
g -> postingsMap.get(ordinalBase[globalToSrcIdx[g]] + (long) globalToNodeId[g]);
```

Postings are written through an **IdentityMapper over Cassandra's own
`globalSrcIdxList` ordering**. With `similarityOrdinals=true` the compactor replaces
the caller's remappers with `buildSimilarityOrdinalMappers(pq)` — a similarity-ordered
permutation — so merged ordinal `g` on disk is a different vector than Cassandra's
`g`. **Every row would bind to the wrong vector.**

The failure is silent. `SegmentBuilder:676` ("row(s) could not be joined to a source
graph ordinal") catches rows with *no* source ordinal; it does not catch rows mapped
to the *wrong* one. The only symptom would be bad recall.

So Run B could only have yielded a crash or a fast-but-wrong index, and a performance
number from a configuration that cannot ship is not worth the wall clock. Aborted at
13 minutes rather than 90.

**Blocked pending two answers from the jvector side:**
1. Is `effectiveRemappers()` the complete contract — is rebuilding the posting lookup
   from `mapping.get(s).oldToNew(...)` sufficient, or does anything else in the output
   depend on the caller's original numbering?
2. Is `setSimilarityOrdinals(true)` intended as the default for this integration? It
   also changes `orderingCache` / `clusterMode` behaviour, which is where Run A
   measured ~239 M exact rescores per merge.

The Cassandra-side fix looks contained — rebuild `globalToSrcIdx` / `globalToNodeId`
(or the `postingsByNewOrdinal` lambda) from `effectiveRemappers()` instead of assuming
identity — but guessing a contract is exactly how the `ReaderSupplier` default-no-op
cost this campaign two full cycles.
