## Hot path — identical, and the prefetch is visibly insufficient

39 of 71 RUNNABLE threads in the read path (32 `readFully`, 7
`copySwapMemory0`). Two distinct stacks, both under `gatherFromOtherSource`:

- **29 threads** via `GraphSearcher.resume` — the anchor-extension path

**The single most useful new observation: `FrontierPrefetchingView` is in
every one of these stacks, and the threads block in `readFully` anyway.**
The frontier prefetch is running and is not covering these reads. That is
direct evidence for the hypothesis behind making `WIDTH` configurable — 3 hints
per expansion cannot hide ~100us of device latency at this miss rate — and it
is why `jvector.compaction.frontierPrefetch` is worth sweeping alongside the
pretouch.

Note also that the seed prefetch only covers the *seeded* branch of
`gatherFromOtherSource`. These stacks are in the `clusterMode` branch
(`clusterSearchL0`), which the seed hint never touches. That explains the
negative result mechanically rather than just empirically.

## What to do with this

1. The A/B is now well-posed: same table state, same build, one flag changed.
   Set `-Djvector.compaction.sourcePretouchMaxNodes=<cap>` and re-run; the
   comparison point is whether a ~31k merge under these conditions stays out
   of the 39–46 band.
2. Consider sweeping `jvector.compaction.frontierPrefetch` in the same
   campaign — the thread dump argues the 3-deep default is the proximate
   reason these reads are not being hidden.
3. If neither helps, the mechanical explanation above points at
   `clusterSearchL0` being the uncovered path, which is a code change rather
   than a knob.
