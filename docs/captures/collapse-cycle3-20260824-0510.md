## Why: the hot path is unchanged, and it is the path prefetch does not cover

90 RUNNABLE threads; the read path dominates exactly as in cycle 1:

| frame | count |
|---|---|
| `MemorySegmentVectorProvider` | 74 |
| `FrontierPrefetchingView` / `processNeighbors` | 67 |
| `FusedPQ$PackedNeighbors.readInto` | 62 |
| `gatherFromOtherSource` / `gatherCandidates` / **`clusterSearchL0`** | 40 |
| `readFully` / `readByteSequence` / `getPackedNeighbors` | 31 |
| `copySwapMemory0` | 6 |

`FileHandleReaderSupplier` appears **0 times** in the dump. For `willNeed` that
is expected — `posix_fadvise` returns immediately, so it is nearly impossible to
catch on a stack. The significant part is what *is* on the stacks: 40 threads in
`clusterSearchL0`.

This confirms the mechanical prediction written into the cycle-1 capture
(`sessions/collapse-20260823-1403/NOTES.md`): the cross-source **seed** prefetch
only covers the *seeded* branch of `gatherFromOtherSource`; these threads are in
the `clusterMode` branch, which the seed hint never touches. Making the
`ReaderSupplier` hooks real made the *existing* hints work — it did not create
hints on the path that is actually starving.

And 67 threads sit in `FrontierPrefetchingView.processNeighbors` while blocking
in `readFully` anyway. `WIDTH` is at its compiled default of 3. Three hints per
expansion cannot hide device latency at this miss rate — the same conclusion the
cycle-1 dump supported, now with the hints actually reaching the device.

## Flags actually in effect

Only two jvector compaction flags are set explicitly:

```
-Djvector.compaction.sourcePretouchMaxNodes=-1
-Djvector.compaction.sourcePretouchWindowNodes=1048576
```

`crossSourceSeedPrefetch`, `frontierPrefetch`, `batchPrefetchDensity` and
`adviseRandom` are **not on the command line** — they are running at their
compiled defaults (ON, 3, 8, true). Worth stating plainly because
`frontierPrefetch=3` is the value the evidence indicts, and nothing in this run
moved it off the default.

## The pretouch cost 6.8 minutes on this merge and bought nothing

**Revised 05:30.** An earlier version of this file said the pretouch was
exonerated at 1.0% of wall clock with per-call work flat at ~3.966M ordinals.
That came from a check script that prints only the last three samples, and it
hid two large outliers:

```
2026-08-23 20:38:51   16,013,399 ord    73,086 ms = 1.2 min  -> 219,104 ord/s
2026-08-24 04:38:28  126,916,949 ord   410,926 ms = 6.8 min  -> 308,856 ord/s
```

39 calls of <=10M ordinals total 239.9 s; these 2 total 484.0 s — **67% of all
pretouch time**. True cumulative is 724.0 s, 2.0% of wall clock.

The 04:38 call warmed 126,916,949 ordinals across **32 sources**. The
30,985-batch merge began 21 minutes later and collapsed anyway. With free at
3 GB against a 1,027 GB table, whatever was warmed was evicted before the
merge's random reads arrived.

`sourcePretouchWindowNodes=1048576` bounds work per source, NOT the total across
32 of them — which is why nine hours of readings looked flat. **Set
`sourcePretouchMaxNodes` to a real bound; `-1` is paying minutes for nothing
above RAM.** The scaling is not explosive (570k ord/s at 4M vs 309k at 127M,
roughly linear with a 1.8x rate penalty); the problem is that the cost is real
and the benefit above RAM is zero.

## What this says to do next

1. **Sweep `jvector.compaction.frontierPrefetch`.** It is the one indicted knob
   still at its default, and it is now genuinely wired to the device. 3 -> 16/32
   is the cheapest experiment available and needs no code change.
2. **Cover `clusterSearchL0`.** This is a code change, and on the evidence of two
   independent captures it is the one that matters. The seed hint covers the
   wrong branch.
3. Do not spend more on the pretouch. It works, it is cheap, and it is not where
   the time goes.
